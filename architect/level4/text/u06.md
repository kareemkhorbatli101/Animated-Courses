# Unit 6 · Eight Things We Assume
%%SUB A list of eight false beliefs, and the code that exists because they are false%%
%%GOALS

Somewhere in your system there is a retry, a timeout, a page of error handling and a budget line for
network traffic. Each of those exists because one of eight statements is false. The statements look
so obviously false when written down that it is hard to believe anybody assumes them — which is
exactly why the list is useful: nobody assumes them out loud.

>
> **The eight assumptions, and what each one costs.**
>
> | The assumption | Because it is false |
> |---|---|
> | the network is **reliable** | every call needs a **timeout**, a **retry** and an **error path** |
> | **latency** is zero | distance costs time; a chatty interface across a continent is unusable |
> | **bandwidth** is infinite | a link **saturates**, and the failure looks like slowness |
> | the network is **secure** | traffic is read and modified unless you prevent it |
> | the **topology** does not change | the address you called yesterday may not be there |
> | there is **one administrator** | three teams, three change windows, three ideas about firewalls |
> | **transport cost** is zero | traffic appears on an invoice, by the gigabyte |
> | the network is **homogeneous** | the two ends differ in version, encoding, clock and conventions |
>
> **Why they are invisible.**
>
> > **Nobody says any of these out loud.** No engineer has ever written *the network is reliable* in
> > a design document. What happens instead is that somebody writes **code that would only be correct
> > if it were**, which is a different thing and much harder to see in review.
> >
> > So the list is not a list of beliefs. **It is a list of the shapes that code takes when a
> > question was never asked** — a call with no timeout, a loop that retries forever, an interface
> > that makes forty round trips, a design that assumes one change window.
>
> **Each one is false by degree.** The network inside one rack is more reliable than the network
> between two continents, and the useful question is never *is this assumption false* but **how
> false, here, today, and what does the code do about it**.
>
> **What the list does not give you.**
>
> - **Any remedy.** It names eight problems and solves none. Retries, idempotency, backoff,
>   circuit breakers and compensation are all somewhere else — three of them in this book.
> - **A measurement.** No thresholds, no figures, nothing to compare against.
> - **A ninth.** Several people have proposed one. There is no agreed list beyond the eight.
> - **A citation you can be confident about.** See the first paragraph.
>
> **What we do, in one line.** Every integration document names **which of the eight it relies on and
> what happens when that fails** — because the assumptions are invisible in code and become obvious
> the moment somebody is asked to name them.
>

### 1 · The second conditional

**1A  Listen and read. Then answer the question below.** %%AUD KS4-06-06%%

> **Lars:** Say why the retry exists.
> **Adeel:** *If the network is reliable, we do not need a retry.*
> **Lars:** That is the zero conditional, which you use for facts, and it makes a false statement
> sound like a rule. The network is **not** reliable, so the condition is unreal: *if the network
> **were** reliable, we **would not need** a retry.*
> **Adeel:** Why *were* and not *was*?
> **Lars:** Because this is the one place English keeps a subjunctive. *If I were*, *if it were*, *if
> the network were* — for an unreal condition, in careful writing. *Was* is extremely common in
> speech and nobody will misunderstand you. In a document, *were* signals that you know the
> condition is false.
> **Adeel:** So the second conditional is for things that are not true.
> **Lars:** For things that are not true, or very unlikely. Compare the three you now have. *If the
> first digit is four, the client made the mistake* — a fact, so present and present. *If we add two
> servers, the queue will shorten* — a real possibility, so present and *will*. *If the network were
> reliable, we would not need retries* — not the case, so past and *would*.
> **Adeel:** Where do I actually use it at work?
> **Lars:** In exactly this situation: explaining why a piece of code exists. **Every retry, timeout
> and fallback in our systems is the answer to a second conditional, and almost none of them says
> which one.** A comment reading *if the network were reliable this would be unnecessary* tells the
> next engineer more than three paragraphs about the implementation.
> **Adeel:** And *unless*?
> **Lars:** Works in the same tense pattern and is shorter: *we would not retry unless the network
> dropped messages*. Use it when the condition is the thing you want to emphasize.

*Why does Lars prefer* were *to* was *in a document?*

**1C  Study the chart.**

| | Example |
|---|---|
| zero conditional — a fact | **If** the digit **is** four, the client **made** the mistake. |
| first conditional — a real possibility | **If** we **add** servers, the queue **will** shorten. |
| second conditional — not the case | **If** the network **were** reliable, we **would not need** retries. |

### 🌐 CULTURE CHECK

Code cannot express an assumption. It expresses behavior, and an assumption is the shape of what is
missing — a call with no timeout, a loop with no limit, an address treated as permanent. That makes
assumptions almost impossible to catch in review, because a reviewer sees what is there. The eight
statements on this list are valuable not because anybody believes them but because writing them down
makes the gaps visible: ask *which of the eight does this rely on?* and a four-line answer appears
that no amount of reading the code would have produced. This generalizes. Any review that only looks
at what was written will miss everything that was assumed, and the only cheap remedy is a short
fixed list of questions that somebody is obliged to answer in words.

**Discuss:** What does your review process ask that cannot be answered by reading the code?

> discovered**, and the path crosses **three administrative domains**. Both are **recorded as
> risks**, with owners, rather than fixed this quarter. **A recorded assumption is a decision; an
> unrecorded one is the February outage.**
>
> **What the list does not give us.** **Any remedy.** Timeouts, backoff, idempotency, discovery and
> compensation are elsewhere — three of them in other sections of this document. **The eight are
> questions, not answers**, and their value is that the questions are **invisible in code**.
>
> **On the source.** The list is usually attributed to **L Peter Deutsch around 1994**, with an
> eighth item added later, and reached most of us through a **later essay**. **There is no single
> canonical publication**, and we say so whenever we cite it.
>
> **Not in this note.** **The other six integrations in this service.** Their assumption tables are
> in sections 6.4 to 6.9, and two of them are still empty.
>
> *Code expresses behavior. An assumption is the shape of what is missing, which is why a reviewer
> cannot see one and a four-line table makes all eight visible at once.*

> **Writer's Tip** — *Do we rely on it?* with the answers *no*, *partly* and *yes* is more useful
> than a tick. *Partly* is where most real systems live and it is the column that starts
> conversations.
