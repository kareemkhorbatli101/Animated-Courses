# Unit 1 · A Description Is Not a Service
%%SUB A document can describe an interface that nobody has built%%
%%GOALS
Use the present simple and the present continuous
Describe what an interface document contains
Say what a description does not prove
%%

A description of an interface is a document. It says what the paths are, what the fields are called
and what comes back. It is extremely useful, and it proves nothing at all about the running system.
This unit is about that gap, about the version of the format that closed one old argument, and about
the sentence *the API supports it* — which, depending on who says it, means two completely different
things.

> ## Meridian · architecture note 13
> *Platform team · interface descriptions · page 1 of 1*
>
> **The specification.** The **OpenAPI Specification, version 3.1.0**, was released in **February
> 2021**. It describes how to write down what an interface looks like, in a single document, in a
> form that both people and programs can read.
>
> **What the document holds.**
>
> | Part | What it is |
> |---|---|
> | the **version** of the format | which rules this document follows |
> | **info** | title, description, and the version of **your** interface |
> | **servers** | where the running systems are |
> | **paths** | the addresses, each with its operations |
> | **components** | blocks defined once and referenced |
> | **webhooks** | notifications the service **sends out** |
>
> **What changed in this version.** Three things matter in daily work.
>
> > First, the schema rules are now **the same rules** as the separate schema specification of
> > **2020-12**. Before this version they were *nearly* the same, and the small differences cost
> > teams whole afternoons. Second, a document **may declare which schema dialect it uses**. Third,
> > **paths is no longer required**: a document may describe only **webhooks**, or only
> > **components**, which is useful for a service that mostly sends rather than answers.
>
> **A description is not an implementation.** This is the sentence to remember. The specification
> describes a format for a document. **It does not run anything, test anything or enforce
> anything.** A perfectly valid document can describe an interface that has never existed, and the
> tools that read it will produce beautiful documentation for a service that is not there.
>
> **What the specification does not do.**
>
> - **It does not check your service.** Nothing in the document proves that the running system
>   behaves as described. That check is a tool you choose and run.
> - **It does not define authentication.** It describes **which** schemes an operation uses. The
>   schemes themselves are other people's documents.
> - **It does not version your interface.** The **info** block holds a version string, and what that
>   string means is your policy, not the format's.
> - **It does not generate code.** Generators exist, they are useful, and they are not part of the
>   specification. Two generators may read one document and disagree.
>
> **What we do, in one line.** The document is generated from the code, the generated document is
> checked against the running service every night, and the words *the API supports* are reserved
> for things that answer a request.
>
> *Source: the OpenAPI Specification version 3.1.0, released February 2021: the top-level fields of
> a document, including the optional paths field and the webhooks field; the alignment of its schema
> rules with the 2020-12 schema specification; and the field for declaring a schema dialect. The
> specification defines a description format only: it does not implement, test, enforce, version or
> generate anything.*

notification the service sends out · **to align** — to make one specification agree with another</sub>

### 1 · Present simple and present continuous

**1A  Listen and read. Then answer the question below.** %%AUD KS2-01-06%%

> **Mei:** Read me your sentence from the release page.
> **Adeel:** *The service is returning a code in the two hundreds.*
> **Mei:** Is that a fact about the service, or a report about this afternoon?
> **Adeel:** A fact. It always does that.
> **Mei:** Then it is the present simple: *the service returns a code in the two hundreds*. Your
> sentence says something different. It says that right now, unusually, that is what is happening —
> which is what you would write during an incident.
> **Adeel:** So the continuous is for now.
> **Mei:** For now, and for temporary situations, and for things in progress. *We are adding the
> operation this week* is correct and useful: it tells the reader this is not finished. *We add the
> operation* would mean we do it regularly, like a habit.
> **Adeel:** Are there verbs that cannot take the continuous?
> **Mei:** A group of them, and they are all over our documents. *Contain*, *consist of*, *mean*,
> *belong*, *depend*, *know*, *include*. The document **contains** nine paths. Not *is containing*.
> These are states, not actions, and a state is not in progress.
> **Adeel:** And *the test system is running an old version*?
> **Mei:** Perfect, because it is temporary and somebody will fix it. **Use the simple for what the
> system does, and the continuous for what we are doing to it.** That one rule will carry most of
> your writing this year.

*What is the difference between* we add the operation *and* we are adding the operation?

### 🌐 CULTURE CHECK

A published document carries the authority of the company whose name is on it, and a reader has no
way to see behind it. That asymmetry is the whole of this unit. Teams know roughly how much to trust
their own documentation — *that page is old*, *ask Ravi about that part* — and none of that
knowledge reaches the page. What reaches the page is a clean, confident description with examples,
and the more professional it looks, the more completely a stranger will rely on it. The remedy is
uncomfortable because it means publishing your own uncertainty: a date of last verification, a
marker on the paths nothing checks. Companies that do this are trusted more, not less, and the
reason is simple — a reader who is told where the soft ground is will walk across the rest without
testing every step.
