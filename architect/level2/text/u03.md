# Unit 3 · Neither Safe Nor Idempotent
%%SUB Sending the same change twice is not the same as sending it once%%
%%GOALS
Use the present perfect
Say whether an operation is safe, idempotent or neither
Say what a retry can do
%%

Some requests can be repeated safely. Ask for a record twice and nothing happens the second time.
Replace a record twice with the same content and the result is the same. But apply a change twice —
*add fifty to the balance* — and you have done it twice. One method in common use is described by
its own specification as neither safe nor idempotent, and almost every client library will retry it
for you anyway.

### 2 · Read

> **Reader's Tip** — When a specification states a property in the negative — *this is not safe* —
> that sentence was written because somebody assumed the opposite.

%%FIG b03-f5 | A one-page internal note: a heading, a line giving the document number and its date, a three-row table of methods with safe and idempotent marked for each, a boxed paragraph on the sentence that says it is neither, a short list of what the document does not define, and a source line in small type at the foot.%%

> ## Meridian · architecture note 15
> *Platform team · partial updates · page 1 of 1*
>
> **The document. RFC 5789**, *PATCH Method for HTTP*, was published in **March 2010**. It adds one
> method to the protocol: a request that **a set of changes be applied** to an existing resource.
> The changes travel in the request as a **patch document**.
>
> **Three methods, two properties.**
>
> | Method | Safe | Idempotent |
> |---|---|---|
> | a read | **yes** | yes |
> | a full replacement | no | **yes** |
> | a partial change | **no** | **no** |
>
> **The sentence to quote.**
>
> > The specification states plainly that this method is **neither safe nor idempotent**. A partial
> > change describes what to do to whatever is there now, so applying it twice applies it twice.
> > *Add fifty* applied twice adds a hundred.
> >
> > The document also gives the remedy in the same place: a request **can be made idempotent** by
> > using a **conditional request** — the client sends the version of the resource it expects, and
> > the server applies the change **only if the resource is still at that version**. The second
> > attempt then fails with a clear status instead of succeeding.
>
> **All or nothing.** The server **must apply the entire set of changes atomically**, and must
> never leave a resource half changed. If any instruction cannot be applied, none of them is.
>
> **The format of the changes is somebody else's document.** This is the part that surprises people:
> the specification **does not define a patch document format at all**. It defines the method. The
> instructions inside the request are written in a format with its own media type, published
> separately, and a server supports whichever ones it chooses.
>
> **So how does a client find out?** There is a response header for exactly that: the server
> announces **which patch formats it accepts**, and the specification says a refusal based on the
> format **should** include that header. A client that guesses the format will be refused, correctly.
>
> **What this document does not do.**
>
> - **It does not define a patch format.** You choose one and name it.
> - **It does not make the method idempotent.** It tells you how to make a request idempotent, and
>   the work is yours.
> - **It does not change retries in your client library.** Most libraries retry by method, and most
>   default lists were written before anybody thought about this.
> - **It does not describe partial responses.** The request is partial; the response is not the
>   subject of this document.
>
> **What we do, in one line.** A partial change carries the version it expects, the server refuses
> it if the version has moved, and our client retries this method only when that marker is present.
>
> *Source: RFC 5789, PATCH Method for HTTP, March 2010: the method, the requirement that the set of
> changes be applied atomically, the statement that the method is neither safe nor idempotent, the
> use of conditional requests to make a request idempotent, and the response header announcing
> accepted patch formats. The document does not define any patch document format.*

at all · **a patch document** — the instructions carried in the request</sub>

### 1 · The present perfect

**1A  Listen and read. Then answer the question below.** %%AUD KS2-03-06%%

> **Lars:** It is twenty past two. Tell me what is happening with the Verano account.
> **Adeel:** The client retried the change three times at two o'clock.
> **Lars:** Is it finished, or is it still going?
> **Adeel:** Still going.
> **Lars:** Then *the client has retried it three times*. The present perfect, because the period is
> not over: you are telling me about now, with a count from the past. *The client retried it at two
> o'clock* is the past simple, and it closes the story.
> **Adeel:** So the perfect is for something unfinished.
> **Lars:** For a result that is still with us. *The limit has been raised twice* — so the limit is
> wrong **now**, and that is why I care. *The limit was raised twice at two o'clock* tells me about
> an event in the past and leaves me to work out the consequence myself.
> **Adeel:** When do I have to use the past simple?
> **Lars:** Whenever you name a finished time. *At two o'clock*, *yesterday*, *on Tuesday*, *in
> March*. You cannot say *we have sent it at nine*. If the time is named and over, the verb is the
> past simple. **A named past time takes the past simple, always.**
> **Adeel:** And *since*?
> **Lars:** *Since* and *for* belong to the perfect, because they describe a period reaching up to
> now. *It has been failing since Tuesday.* *We have had this problem for three weeks.* **That is
> the most useful pattern on an incident call: the perfect with *since* tells somebody how long they
> have been living with something without knowing it.**

*Why can you not say* we have sent it at nine?

### 🌐 CULTURE CHECK

A library default is a decision somebody made once, for everybody, without knowing your system —
and it arrives with the authority of something that has been working for years. *Retry on timeout*
is a good default and a famous source of duplicated money, and the two facts are not in conflict:
it is right for most of what most people send and wrong for the one method whose own specification
says so. What makes this hard is that the cost lands somewhere else. The team that ships the library
never sees the double-charged customer; the team that gets the complaint never reads the library's
default list. The habit worth building is small and unpopular: when you adopt a tool, read the
defaults it chose for you and write down the ones you have decided to keep.

**1C  Read the model text.**

> ### Field note · changing a record
> *Platform team · interface document, section 3.4 · 20 February*
>
> **Every operation, classified.**
>
> | Operation | Safe | Idempotent | May a client retry? |
> |---|---|---|---|
> | read an account | **yes** | yes | freely |
> | replace an account | no | **yes** | freely |
> | change part of an account | **no** | **no** | **only with a version marker** |
> | delete an account | no | **yes** | freely |
>
> **The version marker.** A partial change **must carry the version the client expects**. We apply
> it **only if the record is still at that version**. From **14 March**, a partial change that
> arrives without one is **refused**.
>
> **Why.** A partial change describes what to do to whatever is there now. **Applied twice, it
> happens twice.** The specification for the method states that it is **neither safe nor
> idempotent**, and offers the conditional request as the remedy. We are taking the remedy.
>
> **What a timeout means.** **That the client stopped waiting.** It does **not** mean the change was
> not applied. On a timeout, a client **reads the record** and compares the version.
>
> **All or nothing.** A set of changes is applied **completely or not at all**. We never return a
> half-changed record.
>
> **The format of the changes.** Named in section 3.5, with its media type. **The method's own
> specification defines no format**; a request in an unsupported format is refused, and the refusal
