# Unit 8 · If the First Digit Is Four
%%SUB Five classes of status code, and what a client does with one it has never seen%%
%%GOALS
Use the zero conditional
Name the five classes of status code
Say whose mistake a code reports
%%

A client asks and a server answers, and the answer begins with a three-digit number. The first digit
is the part that matters: it tells the client which of five things happened. If the first digit is
four, the client made the mistake. If it is five, the server did. A system that knows only the
numbers it has seen before is a system that breaks on the first new one.

> ## Meridian · architecture note 8
> *Platform team · status codes · page 1 of 1*
>
> **The document. RFC 9110**, *HTTP Semantics*, was published in **June 2022**. It replaced a group
> of earlier documents from 2014, which in turn replaced one from 1999. **The classes have not
> changed in that time.**
>
> **Five classes, given by the first digit.**
>
> | First digit | Class | Meaning | Example |
> |---|---|---|---|
> | **1** | informational | the request was received; work continues | 100 |
> | **2** | successful | the request succeeded | **200**, 201, 204 |
> | **3** | redirection | further action is needed to complete it | 301, 303, 307 |
> | **4** | **client** error | the request was wrong | **400**, 404, 409 |
> | **5** | **server** error | the server failed to fulfill a valid request | **500**, 503 |
>
> **The rule about unknown codes.** A client **is required to understand the class** of a status
> code, and **may treat a code it does not recognize as the first code of that class** — a code in
> the four hundreds it has never seen is handled like 400. This is why new codes can be added
> without breaking clients that were written years earlier.
>
> **So a client has five behaviors, not fifty.**
>
> > Write the five first, by class. Then add exact codes only where the behavior genuinely differs:
> > a 404 and a 409 are both client errors, and your code may well treat them the same way.
> >
> > **A client with a list of codes is a client that fails on the next one.** A client with five
> > classes and a log line is a client that reports something useful and keeps running.
>
> **Two codes whose names mislead.** The code **401** is called *Unauthorized*, and it means
> **unauthenticated**: the server does not know who you are. The code **403** means the server knows
> who you are and **refuses**. Teams swap these two constantly, and the person who suffers is the
> one reading the log.
>
> **New codes are registered.** The list of status codes is a **registry maintained by IANA**. A new
> code is added to the registry rather than announced in a new protocol, so **the set of codes is
> open and the set of classes is closed**.
>
> **What this document does not define.**
>
> - **What your error body looks like.** The shape of the message beside the code is somebody else's
>   document, and ours is described in section 2.4.
> - **Which errors to retry.** Some responses carry a field saying how long to wait; most do not, and
>   the decision is yours.
> - **Your business rules.** Whether a refusal is a 403 or a 409 is a design decision in your
>   product, made by people.
>
> **What we do, in one line.** Handle five classes, log the exact code, and never crash on a number.
>
> *Source: RFC 9110, HTTP Semantics, June 2022, which replaced the 2014 specifications: the five
> status classes and their meanings; the requirement that a client understand the class of a status
> code and the permission to treat an unrecognized code as the first code of its class; and the
> maintenance of the status code registry by IANA. The document does not define error body formats,
> retry policy for your application, or which code your business rules should use.*

### 1 · The zero conditional

**1A  Listen and read. Then answer the question below.** %%AUD KS1-08-06%%

> **Marek:** Say the rule for the four hundreds.
> **Adeel:** If the first digit is four, then the client will have made a mistake.
> **Marek:** Too many words and the wrong tense. This is a rule that is always true, so both halves
> are present simple. *If the first digit is four, the client made the mistake.* No *will*.
> **Adeel:** Why no *will*?
> **Marek:** Because nothing is being predicted. *Will* is for the future. This is a fact about the
> protocol, like *water boils at a hundred degrees*. We call it the zero conditional, and most of a
> specification is written in it.
> **Adeel:** Can I use *when* instead of *if*?
> **Marek:** Here, yes, and the difference is worth knowing. *If* leaves the condition open: it may
> happen, it may not. *When* says it will happen sometime. **If the first digit is four** — it may
> be. **When a new code appears** — it will.
> **Adeel:** And the comma?
> **Marek:** If the condition comes first, put a comma after it. If it comes second, no comma: *the
> client retries if the response says to wait*. **Both orders mean the same thing, and the condition
> goes first when it is the part you want read.**

*Why does Marek remove* will *from Adeel's sentence?*

**1B  Underline four zero conditionals in 1A.**

**1C  Study the chart.**

| | Example |
|---|---|
| **if** + present, present | **If** the digit **is** 5, the server **failed**. |
| **when** + present, present | **When** a code **is** unknown, the client **uses** the class. |
| condition second, no comma | The client **retries** if the response **says** to wait. |
| negative condition | **If** the code **is not** in our list, we **log** it. |

> **Grammar Note** — Never use *will* in the *if* half of a conditional. *If the digit is four* —

### 🌐 CULTURE CHECK

The design in this unit is a small lesson in how long-lived systems are built: a closed set of five
classes, an open set of codes, and a written instruction about what to do with a value you have never
seen. Almost every protocol that has survived three decades has that shape somewhere, and almost
every system that breaks on a Tuesday broke because somebody replaced the rule with a list. The list
is not laziness — it is written by somebody who can see all the current values and cannot see next
year's. What makes it a habit rather than a mistake is that a list always works on the day it is
written, and the cost arrives later, in another team, usually in a different company. *Handle the
class, log the value* is the whole of the discipline, and it applies far beyond status codes.

**Discuss:** Where else in your systems do you have a list that should be a rule?
