7.1  System development controls
Controls are cheapest when they are designed into a system and most expensive when they are added afterwards. System development controls are the ones applied while the system is being built, and Figure F407-02 names the five things they protect.
Figure F407-02. What system development controls protect
What development controls protect (E.2.c)
What it means
How it is achieved
Accuracy
The system computes what it is supposed to compute
Test with known data and compare the result
Validity
Only genuine, authorized transactions are processed
Authorization checks designed into the program
Safety
Data is not lost or corrupted when something fails
Recovery routines and transaction rollback
Security
Only the right people can reach the system
Access rights built in, not added afterwards
Adaptability
The system can be changed as the business changes
Documentation and modular design
Over all of them
Users involved, stages approved, testing in a separate environment, changes controlled
The system development controls of Chapter 12
Adaptability is the one candidates overlook. A system that cannot be changed safely will be changed unsafely, because the business will not stop to accommodate it. Documentation and modular design are control matters, not merely technical housekeeping.
Across all five sits a familiar requirement. Users are involved from the start, each stage is formally approved, testing is carried out in an environment separate from the live one, and every later change is controlled. Chapter 12 returns to the development life cycle in full.

7.2  Input, processing and output controls
Figure F407-03 shows the three stages and what each one asks.
Figure F407-03. Input, processing and output controls, and what each asks.
The economics are the whole argument for input controls. An error caught as it is keyed costs a moment. The same error found in the output has already passed through every calculation in between, and tracing it back through them costs far more than preventing it would have.
Figure F407-04 sets out the input controls the exam names.
Figure F407-04. Input controls and what each one tests

What it tests

Validity check

Check digit

Financial, hash or record count compared before and after
Twenty invoices entered; twenty posted
Closed-loop verification

Batch totals come in three kinds and the distinction is tested. A financial total adds amounts; a record count counts documents; a hash total adds something meaningless, such as supplier numbers, purely so that a change shows up. The hash total has no accounting meaning at all, which is exactly why it works.
Processing controls keep the data right while it is being handled: run-to-run totals carry a figure from one stage to the next, sequence checks confirm nothing is skipped, and error logs capture what was rejected. Output controls then reconcile what left against what entered, send reports only to named recipients, and dispose of them securely.

The distinction between incremental and differential backups is the one the exam tests. An incremental copies what has changed since the last backup of any kind. It is quick to take and slow to restore, because every incremental since the last full backup must be applied in order. A differential copies what has changed since the last full backup. It grows larger each night but needs only two restores.
Two further points are worth knowing. Mirroring protects against a disk failing but not against a mistake, because the error is copied faithfully to the mirror. And a copy that cannot be altered or reached online is now the standard protection against ransomware, which otherwise encrypts the backups along with everything else.
EXAM TRAP   RAID is not a backup
Mirroring and RAID give resilience against hardware failure. They do not protect against deletion, corruption or encryption, because whatever happens to the original happens immediately to the copy. A question offering RAID as the answer to data loss is offering the wrong answer.

7.4  Reading a flowchart for controls
A flowchart draws a process as a sequence of steps, decisions and documents. For a control reviewer it does something no written procedure does: it shows, in one picture, who holds which duty and where a document is created or lost.
Figure F407-06. A purchasing flowchart read for control weaknesses.
Figure F407-06 shows the redesigned Orontes purchasing cycle. Four questions answer most of what a reviewer needs. Who performs each step, and does any one name appear too often? Where are the decision points, and what rule governs each? Which documents are created, and are they accounted for? Does anything leave the chart without a check?
Applied here, the chart shows four different people, a decision point governed by a stated limit, and a document at every step. The weakness the chart would have revealed before the redesign was a single name appearing in four boxes.

7.5  Extended Example 7A: a batch of invoices, and where each control catches it
This example follows one batch of twenty supplier invoices through the Orontes system and shows which control catches which error. It is exam-core: questions give an error and ask which control would find it.
1. The batch
Accounts payable keys twenty invoices as one batch. Before keying, the clerk records three batch totals: twenty documents, a financial total of the invoice amounts, and a hash total of the supplier numbers.
2. Four errors occur
One invoice is keyed with the quantity in the rate field. One carries a supplier number that does not exist. One is keyed twice. And one is for a supplier that exists, but with a mistyped number that happens to belong to a different real supplier.
3. Which control catches which
The field or format check rejects the first as it is keyed. The validity check rejects the second, because the code is not on the master file. The record count catches the third: twenty-one documents posted against twenty counted.
4. The one that is hardest to catch
The fourth error passes the validity check, because the mistyped number is a real supplier. It passes the record count and the financial total, because the amount is right. Only the hash total of supplier numbers catches it, or closed-loop verification showing the supplier name on screen before the clerk confirms.
5. Why that matters
This is the case that justifies the hash total, which otherwise looks like arithmetic for its own sake. A total with no accounting meaning catches an error that every meaningful total misses, because the error substitutes one valid value for another.

Chapter summary
Figure F407-08 brings the chapter together.
Figure F407-08. Chapter 7 summary map: the key rule for each section.
System development controls protect accuracy, validity, safety, security and adaptability, and they are cheapest when designed in rather than added afterwards. Input controls catch errors where correction costs least, through field, format, range, reasonableness and validity checks, check digits, batch totals and closed-loop verification. Processing controls keep the data right in transit and output controls reconcile what leaves against what entered. Storage controls run full, incremental and differential, with an off-site copy and an immutable one, and mirroring is not a backup. A flowchart shows in one picture who holds which duty and where a document is created or lost.
